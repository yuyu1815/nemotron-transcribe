# 話者付き文字起こし

Windows の AMD GPU で ReazonSpeech による日本語音声認識と Nemotron-3-Diarization による話者分離を行います。動画 URL ではメタデータと場面画像もまとめて保存します。

## 実行

```powershell
mise install
mise run setup
mise run transcribe "C:\path\video.mp4"
# または
mise run transcribe "https://www.youtube.com/watch?v=VIDEO_ID"
# チャンネル全体・再生リスト（列挙しながら順次処理）
mise run transcribe "https://www.youtube.com/@Yukkuri_matcha" --download-workers 2
mise run transcribe "https://www.youtube.com/playlist?list=PLAYLIST_ID" --download-workers 2
```

進捗は標準エラーに表示します。端末では1つの表に動画ごとの URL・タイトル・現在の工程・転送量/ASR 区間数・経過時間を表示し、処理中の動画と直近3件の完了結果を残します。列挙中は総数未確定と表示し、発見数と保存・スキップ・列挙時除外・失敗の件数を集計します。リダイレクト時は表を使わず、**各動画 URL を先頭に付けた**工程開始・終了と間引いた進捗を改行で記録します。

URL はメタデータ取得・ダウンロード後、**場面画像生成と音声処理を同じ動画内でも並行**して進め、両方の成功を回収してから公開します。音声側は「音声抽出 → 話者分離 → 区間 WAV 作成 → 文字起こし・ログ作成」です。進捗は画像・音声それぞれの工程・詳細・経過時間を独立して表示し、URL に直列の段階番号は付けません。ローカル入力は従来の音声3段階表示を保ちます。転送進捗は転送ごとの実バイト数と割合（総量が推定なら「推定」、不明ならバイト数のみ）で、動画全体の推定割合ではありません。ASR は完了区間数/総区間数を表示し、リダイレクト時は約1割ごとの実カウント（初回0と最終値を含め最大11回）に絞ります。終了・失敗時は最新の実カウントを表示します。進捗は成果物に含めません。標準出力の `Saved:` は表を閉じてから、今回保存したパスだけをまとめて表示します。

ダウンロードは既定 **2件並列**（`--download-workers N`）、音声処理は既定 **2工程並行**（`--processing-workers P`）、画像生成は既定 **2動画並行**（`--image-workers I`）です。1動画の画像枝内では PNG 検証・一覧画像作成に既定 **2ワーカー**（`--image-render-workers R`）を使います。4オプションとも URL のみ・正の整数です。P は動画の生存期間ではなく、**実行中の音声工程数**の上限です。`--processing-workers 1` でも画像と音声の並列実行は継続し、音声工程同士だけが直列になります（Nemo と ASR は重なりません）。取得も独立して進みます。

取得結果と `result/video.txt` を一度だけ準備してから、画像枝と音声枝へ分けます。音声の「準備（共通 WAV の抽出のみ）→ Nemo 話者分離 → CPU で区間 WAV 作成 → ASR・ログ」はそれぞれ独立した1枠です。準備と区間 WAV 作成を合計1枠には制限せず、P が許せば並行できます。画像生成中でも**同じ動画の ASR まで進み、ASR 完了後は画像を待たずに音声枠を返します**。公開待ちは調整役が保持し、ASR スレッドは画像 future を待ちません。

モデルを待つ動画はキューに残し、スレッドや P 枠を占有しません。例えば A の ASR 実行中に B が ASR 待ちでも、C の Nemo を実行できます。また、B の WAV 抽出中に A の区間 WAV 作成から ASR へ進めます。実行可能な ASR、Nemo、区間 WAV 作成、準備の順で選び、各待ち列内は FIFO です。区間 WAV は ASR 枠を予約する前に作ります。画像は専用の有界 FIFO 待ち列と別プールで実行します。

完了して未回収の取得・画像・音声結果、全待ち列、片枝完了後の公開待ちを含め、一時領域を保持する動画は最大 **N + P 件（既定4件）**です。画像枠 I を増やしても保持動画数は増えません。取得 future は完了未回収も含め N 以下、音声 future は P 以下、画像 future は I 以下です。同じ動画の一時領域を引き継ぎ、両枝の結果を回収・削除してから保持枠を返します。チャンネル全件の取得は待たず、先に取得できた動画から両枝へ進めます。

モデルはバッチ全体で **Nemotron 子プロセス1個＋ネイティブ ASR 子プロセス1個**を共有・常駐させます。各モデルは初めて必要になった時だけロードし、動画・ASR 区間ごとには再ロードしません。全件スキップならモデル子プロセスは起動しません。ローカル入力も同じ共有モデル経路です。通信は標準入出力で、待受ポートは使いません。

話者分離と ASR は**別々のサービスロック**を持ちます。同じ Nemotron の forward、および同じ ASR セッションの要求はそれぞれ直列です。ASR は**共有重みのネイティブ複数ストリームバッチ推論**を行います。単なる動画間のパイプライン化ではなく、1要求の複数区間をまとめて DecodeStreams します。ASR インスタンスの複製や同じ DirectML セッションの並行 Run は行いません。

`--asr-batch-size B` は URL・ローカル両方で使え、**既定4、整数1～32**です。1 は複数ストリーム化を無効にする物理メモリ調整用の設定です。1動画内の区間を、最低0.5秒の無音追加後の実サンプル長で安定ソートし、指定件数以下かつ「件数 × 最長秒数」が **60秒以下**になるようまとめます。30秒超の区間は必ず単独で、分割・切り捨てません。各結果を元のサンプル位置・区間終端で検証し、元の区間順に戻して保存します。動画をまたぐ動的バッチ基盤はありません。

60秒はパディング量に基づく**メモリ予算のヒューリスティックであり、VRAM 使用量の保証ではありません**。GPU に合わせて B を下げてください。OOM 時の自動縮小再試行・CPU フォールバック・モデル再起動はしません。バッチのパディングは認識結果にも影響し得ます。**今回の画像並列化・工程スケジューラ・バッチ推論による速度向上は未測定**で、性能改善や VRAM 不足の回避を保証しません。

```powershell
mise run transcribe "C:\path\video.mp4" --asr-batch-size 4
mise run transcribe "https://www.youtube.com/playlist?list=PLAYLIST_ID" --processing-workers 2 --image-workers 2 --image-render-workers 2 --asr-batch-size 1
```

初回 ASR は常駐する実セッションでウォームアップし、プロファイリングを終了して実際の非 Memcpy DirectML ノード実行を確認してから要求を受け付けます。初回ロード・モデル待機・推論状態は既存の工程表示へ反映します。通常処理では区間ごとの旧 CLI プロファイル検証は不要です。

**旧方式のバッチが動作中なら、完了を待つか、その端末で Ctrl+C して終了を確認してから新方式を起動してください。** 実行中の旧親プロセスは新方式へ切り替わりません。同時起動すると旧・新モデルが VRAM 上で重複します。完成済み出力は再実行時にスキップされます。

ローカルの動画・音声ファイルは従来どおり入力の隣に `video.transcript.log`（文字起こし）と `video.speakers.log`（話者区間）だけを保存します。ログは UTF-8、各行は `[時:分:秒.ミリ秒 - 時:分:秒.ミリ秒] 内容` です。

動画 URL、および YouTube のチャンネル/再生リストに対応し、各動画についてプロジェクト直下に次を保存します（ID は安全なファイル名に変換）。`video.txt` の URL は入力のチャンネルではなく、その動画自身の URL です。重複動画、判明した非公開/削除動画、未完了のライブ・配信予定は除外します。動画の詳細取得後もライブ状態を再確認し、未完了ならスキップします（列挙時に判明した除外は `excluded`、投入後のスキップは `skipped` に集計）。

```text
output/<ID>/
  video.txt                    # タイトル・URL・再生回数・投稿日・取得日時・概要欄
  transcript.log
  speakers.log
  images/
    <開始時刻>--<終了時刻>.jpg  # 最大114場面の一覧画像
    full/<撮影時刻>.png        # 各場面の中間に近い実フレーム、元解像度
```

URL のダウンロード・WAV・TSV・生成途中の結果は `.work/batch-run-*/video-*/` の動画ごとに独立した一時領域に置きます（ローカル入力は `.work/temp-run-*/`）。共有モデルのウォームアップ用 WAV・GPU プロファイルは同じ実行領域内の `models/` に置き、動画枠には数えません。URL の結果はすべて完成後、同一ボリューム上のディレクトリ rename でまとめて公開します。成功・スキップ・失敗後にその動画の一時領域を削除します。

再実行時は最新の詳細メタデータを取得し、既存 ID フォルダー内の `video.txt` の固定ヘッダー URL、正確なファイル構成、空でないログ、画像の形式・時刻名・枚数・寸法・ページ範囲の整合性を確認します。**同じ動画の完成済み出力と保守的に認識できた場合だけ、メディア取得/GPU 処理前にスキップ**します。これは構造と画像デコードの検証であり、ハッシュによる完全性保証ではありません。不完全な出力・別 URL・未知の構成・シンボリックリンク等は衝突エラーにします。既存データの上書き・削除・不足分の補完はしません。公開時の競合でも既存データを保護し、ローカルの既存ログも上書きしません。

動画単位の取得・メディア検証・既知の入力不良は URL と理由を表示して他の動画を続け、1件でも失敗があれば最終終了コードは非0です。片枝が失敗するとその動画をキャンセルし、未開始の画像・音声工程を取り除きます。実行中の兄弟枝の終了と結果回収を待ってから一時領域を削除し、動画の失敗を1回だけ集計します。画像だけ・ログだけの部分結果は公開しません。列挙に失敗した場合は追加投入を停止し、投入済み動画を処理してから非0で終了します。一方、**共有モデルの故障はバッチ全体を停止**します。自動再ロード・旧 CLI への再試行・CPU フォールバックはしません。Ctrl+C も全枝の新規投入を止め、所有するモデル子プロセスを要求ロックを待たず中断して待機要求を解除し、ダウンロード・音声・画像の3プールと画像内部ワーカー・子プロセスの終了を待ってから実行用一時領域を削除します。実行中の FFmpeg は強制終了せず終了を待ちます。メタデータの HTTP 呼び出し中などはネイティブのタイムアウトを待つ場合があります。各処理は主要工程間・ASR バッチ間と公開前に停止を確認します。完成して公開済みの結果は残ります。

### URL の場面検出オプション

```powershell
mise run transcribe "https://www.youtube.com/watch?v=VIDEO_ID" --scene-threshold 0.12 --min-scene-seconds 0.6
# 検出する領域だけを限定（画像は全画面のまま）
mise run transcribe "https://www.youtube.com/watch?v=VIDEO_ID" --scene-crop 100 50 1800 1000
```

FFmpeg ネイティブの scene score（有限値 0～1、既定 0.12）と最短場面秒数（有限値 >0、既定 0.6）を使います。既定は全画面。crop は `LEFT TOP RIGHT BOTTOM` の整数ピクセル座標で、右端・下端は含みません。これらのオプションや `--download-workers`・`--processing-workers`・`--image-workers`・`--image-render-workers` をローカル入力に指定するとエラーです。

画像と音声は同じ最終ダウンロード動画から作り、コンテナ開始時刻を共通の 0 秒にします。音声開始が遅れる分は無音で補います。画像は ffprobe の実フレーム PTS と FFmpeg の抽出 PTS を照合し、VFR でも FPS 換算や時刻 seek に依存しません。欠損・逆行・矛盾した時刻や未確定の終端は検証エラーになります。任意のタイムスタンプ不連続を修復する機能ではありません。

## 準備と制限

- Windows 11 x64、対応 AMD GPU と AMD の ROCm 対応ドライバーが必要です。ドライバーは自動変更しません。Python と uv は mise で管理します。
- `mise run setup` は必要なモデルを固定リビジョンから取得し、不足・破損している DirectML 実行体を [sherpa-onnx の fork](https://github.com/yuyu1815/sherpa-onnx/tree/windows-directml-reazonspeech) の固定コミットからビルドします。既存の正常なモデル・実行体は再利用します。準備後に ROCm と DirectML を GPU で確認します。
- 既存環境へ共有 ASR ワーカーだけを追加する場合は `mise run setup-asr-worker` を実行します（`uv run --locked --no-sync python setup_project.py --asr-worker-only`）。旧実行体とは別の追加成果物を使います。成果物がない・検証に失敗した場合、新方式はエラーで停止し、旧 CLI に戻しません。
- Git と `ffmpeg`・`ffprobe` がない場合、また実行体のビルドに必要な CMake・Visual Studio C++ Build Tools・Windows SDK がない場合は、Windows の `winget` 等を使い追加します。初回ビルドにはインターネット、数 GB の空き容量と時間が必要で、権限確認や再起動が必要になる場合があります。詳細は `docs/directml-build.md` を参照してください。
- ASR は DirectML と CPU の混在実行です。GPU が使われていない場合はエラーにします。DirectML は DXGI のデバイス 0、話者分離は ROCm のデバイス 0 を使います。複数 GPU の場合は各デバイスを別途確認してください。
- 先に Nemotron で発話区間を推定し、各区間の元の混合音声を ReazonSpeech に渡します。話者ログでは、連続する同じ話者の区間の間隔が 0.5 秒以下なら一続きとして表示します（別の話者が間にあれば結合しません）。文字起こしの区間は結合せず、元音声基準の時刻で照合します。短い間隔に発話があるとは限らず、これは見やすくするための補間です。話者分離が検出しなかった発話は文字起こしされません。
- 重複区間は各話者についてそれぞれ処理しますが、音源分離は行いません。同じ混合音声を複数回認識するため、相手の発話や重複したテキストが含まれる場合があります。
- 短い区間は DirectML の実行のため末尾に無音を追加して最低 0.5 秒にします。追加した無音に対応するトークンは除きますが、認識結果はパディングの影響を受ける場合があります。区間の時刻は変更しません。
- 区間は 30 秒を超えても分割しません。ReazonSpeech は約 30 秒までの入力を想定しており、長い区間では認識精度低下や GPU メモリ不足が起こり得ます。30秒超は単独要求として従来どおり受け付け、単独の場合は60秒のバッチ予算でも拒否しません。この互換経路は長時間入力のメモリ不足を防ぐものではありません。
- 話者分離は全音声を一度に処理するため、音声が長いと GPU メモリ不足になる可能性があります。一時 WAV・区間 WAV・GPU プロファイル用の空き容量も必要です。
